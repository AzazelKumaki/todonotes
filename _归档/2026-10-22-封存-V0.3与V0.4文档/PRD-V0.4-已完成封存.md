V0.3（M3）已交付：云同步（三种自带后端）+ 配置码 + 真机全屏适配，13 条硬规则全部保持。  
V0.3 PRD 里明确**推迟**到 M4 的项 + 日常使用中暴露的短板，构成本版范围：

### 1.2 M4 的三条硬指标

1. **APK 自己知道有没有新版本**：检查 → 下载 → 引导安装，全流程真能用。
2. **配色随你换**：八套预设 + 取色器自选，两个域各一套，跟着域切换；**状态栏图标按明暗自动深色 / 浅色**。
3. **云端数据多加一把锁**：上传前用同步口令派生密钥做 AES-GCM 加密，口令不进日志、不进备份。

### 1.3 本地优先（本版产品底线，不可让步）

APK 离线可用、网页双击可用；云同步与加密都只是可选外挂——  
加密没开 / 打不开 / 口令忘了，都**不许**阻塞任何本地操作（规则 13 同口径）。

### 1.4 明确不做（避免范围蔓延）

- 子任务 → 已拍板进 **V0.5**（见 §11.1）
- ~~到期提醒（应用内）~~ → ❌ **已删除**（2026-10-19 拍板），当初为什么做不了推送见 §11.3
- 内置云通道 / 免密钥 AI（旧 FR-313）→ ❌ **永久移除**（2026-10-19 拍板），理由见 §11.4
- 逐字段合并 → 仍是整包快照 + 冲突弹窗，不动
- 换存储引擎（localStorage → IndexedDB）→ ❌ **不做**，而且不是"以后再说"：
  `file://` 下 IndexedDB **实测打不开**（实测方法与证据见 §8 坑 35），网页双击形态下这条路根本不通

## 5. 分步开发清单（按依赖顺序，每步可单独验证）

### S1 · 在线更新（FR-401）　复杂度：中

**版本源 = GitHub Releases（2026-10-19 拍板）**，仓库 `AzazelKumaki/todonotes`（公开）。

```
GET https://api.github.com/repos/AzazelKumaki/todonotes/releases/latest
Accept: application/vnd.github+json
→ { tag_name:"v0.4", body:"更新说明正文", assets:[{name:"待办清单-V0.4.apk", browser_download_url:"https://…"}] }
```

✅ **已实测的两条事实**（决定这个方案成不成立）：
1. GitHub REST API 返回 `Access-Control-Allow-Origin: *` ⇒ **`file://` 双击打开、APK 本地壳里都能直连**，不用中转服务器、不用备案。
2. ⚠️ 该仓库**目前还没有任何 Release**（`/releases/latest` 现在返 404）⇒ 发 V0.4 前**必须先补一个 Release**（tag `v0.4` + 上传 APK 附件），否则"检查更新"永远查不到东西。查不到 / 网络失败一律**静默**，遵守规则 13。

字段映射（写死即可）：版本号 ← `tag_name` 去掉开头 `v`；更新说明 ← `body`；安装包 ← `assets` 里第一个以 `.apk` 结尾的 `browser_download_url`；检查时间 ← 存 `upd`。

1.（字段映射见上文）
2. 网页侧 `UPD.check()`：fetch 一次（5 秒超时 + try/catch，失败静默，遵守规则 13）；  
   比对本机版本（`AppBridge.getVersionName()` 或 `APPVER`）。
3. 「我的 → 检查更新」改为真检查：最新 → 显示"已是最新（v0.4）· 刚检查了"；有新版 →  
   显示版本号 + body 正文 +【下载并安装】。
4. 下载：`fetch(apkUrl)` → ArrayBuffer → 分块走现有 `AppBridge.writeBegin/writeChunk/writeEnd`  
   落进「下载 / 待办清单」→ 跳系统安装向导（`Intent.ACTION_VIEW` + MediaStore uri +  
   `REQUEST_INSTALL_PACKAGES`——先试 MediaStore uri，不行再加 FileProvider）。
4b. **下载兜底（必须有）**：GitHub 附件在国内可能慢或打不开 ⇒ 除了【下载并安装】，
   再给一条【下载慢？到发布页手动下载】：浏览器打开 Release 页面，保留手工升级这条路不断。
4c. 未认证请求限流 60 次/小时/IP —— 自用绰绰有余，不管。
5. 网页端（非 app-mode）：按钮点击后提示"网页版随 index.html 更新"。

### S2 · 换配色 + 状态栏随明暗（FR-402/403）　复杂度：中　✅ 已完成

> 这是本次**改过方案**的一项：原计划做「自定义背景图」，2026-10-19 用户拍板砍掉 ——
> 理由两条：**① 一张图要占用约 1.4MB，和待办数据抢那点可怜的本地空间，本末倒置
> ② 效率软件花力气调自己去伺候一张图，不划算。**改成配色，同样的「一眼分辨工作 / 生活」，代价几乎为零。

1. **八套预设**（`THEMES`）：静水蓝 / 珊瑚 / 苔绿 / 紫藤 / 玫瑰 / 湖青 / 琥珀 / 石墨。
   每套五值：`brand / brand2 / bg / soft / brandink`（主色 / 浅色版 / 页面底 / 淡底 / 深字）。
2. **取色器**：`<input type="color">` 选一个主色 → 其余四值自动派生
   （`brand2`=主色混白 30%、`soft`=混白 86%、`bg`=混白 95.5%、`brandink`=混黑 22%），
   保证任何自选色下**页面底都是浅色、卡片文字读得清**。
3. **怎么套上去**：CSS 里 `.theme-*` 那几条规则只管**形状**（圆角 / 间距），
   颜色由 JS 写进 `body.style` 的 CSS 变量（inline 优先级最高，又不用新建一套 class）。
4. **存在哪儿**：`localStorage` 独立 key **`todo.theme.v1`**，`{work:{k,custom,brand}, life:…}`。
   ⚠️ 不进主 DB —— 沿用 S2 老方案的教训：主数据那一坨 JSON 是命根子，能不往里塞就别塞。
   顺带的便宜：导出 / 备份 / 配置码 / 云同步只读主 DB，配色天然不在里面。
5. **第③栏「我的」保持中性灰**：`applyTheme` / `clearThemeVars` 在 tab=me 时把变量摘掉（设置与域无关）。
6. **FR-403**：`themeLum(bg) > 0.45` → `AppBridge.setBarsDark(true)`。
   原生 `MainActivity.Bridge.setBarsDark` 已加 `@JavascriptInterface`（跑在 WebView 线程，内部 `runOnUiThread`）。
7. 测试 `tests/theme.js`（23 项）：预设合法、自定义派生、两个域独立、切域换色、
   「我的」页还原中性、状态栏明暗、**导出里不含配色**、旧入口「背景图」已彻底移除。

### S3 · 回收站自动清理（FR-404）　复杂度：低　✅ 已完成

1. `DB` 加 `lastPurge`（随主数据落盘）；`init()` 里扫，**当月扫过就跳过**。
2. 扫：`t.deleted && deletedAt 的日期 < (今天-30天)` → 真删。
   ⚠️ 两个保守口径：**只比日期不比时刻**（整 30 天那条当天还能翻出来恢复）、
   **没有 `deletedAt` 的老数据永远不动**（宁留不误删）。
3. 删除入口补 `t.deletedAt=nowStamp()`（原先只有 `deleted=true`，无从判断放了多久）。
4. 删了就 toast「回收站清理了 N 条（超过 30 天）」；一条没删就静默。
5. 测试 `tests/trash-purge.js`（12 项）：31/40 天的删、29/30 天的留、老数据不动、本月不重复扫。

### S4 · 云端加密（FR-405）　复杂度：高　✅ 已完成

1. `CLOUD` 加能力：**`wantEnc / encKey / wrap / unwrap`**（只用 WebCrypto）。
2. 密钥派生：`PBKDF2-SHA256(同步口令, SALT+'.enc.v1', 100k)` → AES-GCM 256 位密钥
   （与 `SYNC.sid()` 同参数体系，但 **salt 刻意不同**，互不影响）。
3. 加解密**只在 `CLOUD.getRow / putRow` 这一层做** —— `SYNC` 与界面一行没改。
   格式：`{__enc:1, alg:'AES-GCM', iv(base64), ct(base64)}`，iv 每次随机。
4. 侧车轮因此多了 ⚠️：**COS 的文件格式变了一点** —— 原来把 todos/CATS 几个字段摊平写在文件里，
   现在统一装进 `payload` 里（密文是一个对象，摊平会把 iv/ct 弄丢）；
   读取时两种格式都认（`p.payload || p`），老的自机数据照读不误。
5. 解密失败（口令换了 / 数据坏了）→ 抛 `ENC`，由 `CLOUD.why()` 翻译成人话：
   **不清本机、不重传**，只说"本机数据一点没动，也没往上传，接着用该怎么办"。
6. UI：云同步配置页加「上传前加密」勾选行。**默认开**（2026-10-19 拍板）。
7. 环境没有 WebCrypto（极少见）→ 直接退回明文，同步照走（规则 13：不阻塞）。
8. 测试 `tests/cloud-enc.js`（19 项）+ `e2e-local-sync.js` 里加了一条端到端断言：
   **直接翻服务器上落的那一行，必须看不到任何待办内容**。
   `browser-check.js`（无头 Chrome 打开 file://）也已验证 `crypto.subtle` 可用、真实同步加密通过。

### S5 · 搜索与筛选（FR-406）　复杂度：中

1. 「记一笔」顶部（固定切换栏下方）加搜索框：输入即过滤当前列表。
   **2026-10-19 拍板：搜标题 + 搜备注**（备注是原话，很多条目就靠它才找得回来），两者都命中时**标题命中排前面**。
2. 筛选行（搜索框下方，可折叠）：象限四格 / 分类（当前域）/ 状态（未完成 / 已完成 / 逾期）。
3. 与现有排序规则叠加：筛选只做"过滤"，**不改排序**（规则 1）。
4. 空结果给一句"没有匹配的 · 清空搜索看看"；`Esc` 或点×清空。

## 6. 数据结构（V0.4 新增）

| 字段 / 结构               | 含义                                                                |
| --------------------- | ----------------------------------------------------------------- |
| **`todo.theme.v1`** | 配色：`{work:{k,custom,brand}, life:{…}}` —— **独立 localStorage key**。隔开的意义：写失败也只是"配色没换成"，主数据（待办/分类/复盘）毫发无损；也因此天然**不进备份 / 导出 / 配置码 / 云端** |

| `t.deletedAt`       | V0.4 新增：删除时刻（`'YYYY-MM-DD HH:mm'`）。没有它的老条目**永远不自动清理** |

## 8. 开发约定与踩过的坑（V0.3 §9 的 29 条全部继承，以下只列新增）

30. **凡是"大块"或"附加"的东西都存独立 key，不进主 DB**：背景图时代立下的规矩，
    配色（`todo.theme.v1`）和在线更新（`todo.upd.v1`）照办 —— 主数据那一坨 JSON 是命根子。
31. **网页 → 原生的新调用**统一走 `AppBridge`（`typeof AppBridge!=='undefined'` 判断），  
    浏览器里自动降级为 no-op；新增方法要在 `MainActivity.Bridge` 里加 `@JavascriptInterface`，
    **改 UI 必须 `runOnUiThread`**（Bridge 方法跑在 WebView 线程）。
32. **加密只用 WebCrypto**（AES-GCM + PBKDF2），不引第三方库；iv 每次随机，密文带版本标记，  
    方便以后换算法。口令/密钥**禁止**进 `console`、备份文件、配置码。
33. **APK 是二进制，不能走 `writeBegin/writeChunk` 那套字符串通路**（编码会坏包），
    也不能一次性塞 Binder ⇒ 传个 https 地址让**原生自己下载**（`AppBridge.installApk`），
    只认 GitHub 自家域名。
34. 每步做完跑对应测试脚本（`tests/` 现有 17 个）；改渲染相关的，顺手跑 `browser-check.js`
    （无头 Chrome 打开 file://，能抓出只在真浏览器里才出现的错误）。
35. **`file://` 下 IndexedDB 不可用（2026-10-19 实测）**：`indexedDB.open()` 既不触发 success 也不触发 error，
    **请求直接挂起超时**；加 `--allow-file-access-from-files` 也一样。而 `localStorage` 在同样条件下正常可用。
    ⇒ 任何"换个更专业的本地存储"的想法，在**网页双击形态下先判死刑**，别浪费时间。
    （实测方法：`tests/_probe_storage.html` + `chrome --headless=new --dump-dom file:///…`，用完删探针）
36. **GitHub Releases API 在没有 Release 时返回 404**，这不是网络错误：检查更新要把 404 当
    "暂时没有新版本"处理，**不能当异常弹错**（规则 13）。

### 11.3 ❌ 已删除：到期提醒 / 系统推送（2026-10-19 拍板）

> 这条**从产品里整个删掉**（连"应用内提醒"也不做），以后不再安排。
> 下面把原因存档 —— 万一哪天真想捡回来，先读完这四个坑。

1. **推送必须有个"随时在线的第三方"替你敲门。** 手机不在你手上时，App 进程早被系统回收了，
   它自己没法在 21:00 醒过来喊你 —— 得由**推送服务**（Google FCM / 各家厂商推送）代为发通知。
2. **FCM 在国内基本不可用，厂商推送要一家家接。** 小米 / 华为 / OPPO / vivo 各有自己的推送 SDK，
   要挨个申请开发者账号（多数还要**企业资质**）、挨个配 AppID / AppKey / AppSecret，
   还得自己搭个服务端定时来发 —— 对一个自用小工具来说，这是十倍以上的工程量换来一个没人管的功能。
3. **就算接好了，国产 ROM 也未必让它活着。** 推送依赖保活，而各家 ROM 恰恰在狠杀保活：
   结果就是推送**时灵时不灵**。一个"可能不响"的提醒，比没有提醒更坑人 —— 你会以为它替你记着。
4. **真正想要的其实是"打开时别错过"。** 这个 App 是**一天要开好几次**的（记待办、勾完成、看清单）。
   在打开时提醒「今天还有 N 件、逾期 M 件」，信息传达的效率跟推送几乎一样，
   还不耗电、不要权限、**不会在你开会时震一下**。

**结论**：这个功能从产品里删干净 —— 不申请 `POST_NOTIFICATIONS` 权限、不做后台服务、
不加设置项、不留占位。**逾期该有的提示已经有了**：列表里逾期项排在前面、日历里红下划线，
那两条就够用，且不需要任何额外代价。
