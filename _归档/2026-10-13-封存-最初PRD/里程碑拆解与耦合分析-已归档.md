## 0. 一句话结论

**当前 40 条需求里，真正卡住"能用起来"的只有 3 件：数据存下来、AI 真解析、数据模型补全。**  
其余 37 条都可以后置或切掉 —— 尤其**云同步、APK、备份三件套、循环安排、全部 P1/P2**，它们与已实现功能**几乎没有耦合**，是纯粹的历史包袱，先切掉不会让已做的东西贬值。

## 3. 关键发现：PRD 缺一个「本地存储」基础需求

这是本次分析最重要的结论。

40 条需求里**没有任何一条**是「把数据存到本机」。持久化被当作**默认存在的前提**，散落在 FR-005（编辑）、FR-013（同步）、FR-018（备份）里隐含假定，没有单独立项、没有验收标准、没有数据实体定义。

后果就是：原型做完了 20 条界面，却完全没有落盘代码（`localStorage` / `IndexedDB` / `fetch` 命中数全为 0），因为**没人被明确要求做这件事**。

> **建议（需你拍板）**：新增一条 P0 需求 **FR-025 本地数据存储**，至少覆盖：  
> ① 待办 / 分类 / 复盘 / 设置全部落盘，刷新与重开不丢；  
> ② 网页端用浏览器本地库，APK 端用 App 私有目录，不申请系统权限；  
> ③ 存储层单独封装一层，日后加云同步只改这一处；  
> ④ 首次打开写入预置 8 个分类，之后以用户数据为准。

## 4. 里程碑划分（目标：最快拿到一个真能用的版本）

**目标**：记一条 → 关掉再打开还在 → 能改能勾 → 日历翻得到下个月。

| 做 | 内容                                                                                       |
| - | ---------------------------------------------------------------------------------------- |
| 1 | **FR-025 本地存储**（新增，见 §3）                                                                 |
| 2 | **数据模型补全**（`createdAt` / `updatedAt` / `source` / `人工决定标记` / `解析状态`）                     |
| 3 | **AI 解析接进来**：先固定「解析服务接口契约」（输入：原话 + 当前时间 + 候选分类；输出：6 字段 JSON），**先用规则版顶着**，真大模型后替换，UI 一行不改 |
| 4 | **日历去硬编码**：真实系统日期、可左右切月                                                                  |
| 5 | **入箱判定按 D-02 新口径**：6 项**全填**才出收件箱，缺任一项即进箱（已拍板）                                           |
| 6 | **排序按 D-01 新口径**：逾期在前 → 逾期内部再按象限排 → 然后是正常四象限（已拍板）                                        |
| 7 | ~~首屏 ≤10 条折叠~~ → **改为不折叠，超出部分下滑**（D-23 已拍板改口径）                                           |
| 8 | **清掉原型里的假数据**：种子 18 条 / `TODAY='2026-10-15'` / 日期锁 2026 / 写死的复盘                          |

**M1 完成判据**：断网状态下，说一句话 → 保存 → 关掉浏览器 → 重开 → 那条还在 → 能勾完成 → 日历能翻到 11 月。

### M2 · 「能带走、能带身上」

导出 JSON/CSV（FR-019）→ 本地自动备份（FR-018）→ 出 APK（FR-015）→ 复盘接真 AI（FR-016/017）。

> 排序理由：**导出排在备份前面** —— 没有云同步时，导出是"数据能带走"唯一真实出口；备份是锦上添花。

### M3 · 「连起来」

云同步（FR-013）+ 云服务配置（FR-014）+ 循环安排（FR-024）+ 从 JSON 导入（FR-110）。

### M4 · 增强

P1 11 条 + P2 5 条，按试用反馈重排。

## 6. 代码层面的切割建议

**UI 层 → 保留复用**：11 个视图的交互与视觉已反复评审过多轮（v2.1~v2.6），四象限色值、两域主色与圆角、日历格 9px 数字 + 6px 圆圈等规格已逐值核对通过。这部分是**资产**，不要重写。

**逻辑层 → 推倒重来**：`doParse()`（正则假解析）、硬编码 `TODAY`、种子数据、写死的复盘、无落盘的状态管理。这部分是**负债**，必须换掉。

**一条硬原则**：先把「解析服务接口契约」定死并单独封装一层（一个函数：`解析(原话, 当前时间, 候选分类) → 6字段`）。这样规则版 / 真 AI / 换服务商，三种情况**前端代码一行都不用改** —— 这是 M1 能快的关键。

## 8. 仍未拍板的取舍（M1 开工前需定）

1. **M1 是否含复盘？** 含 → 多 1~2 天（依赖 AI，且要过语气红线）；不含 → 日历里先隐藏复盘区块，M2 再开。
2. **AI 是先接真模型，还是先用规则版顶着？** 规则版 → M1 最快，但"说一句话自动填好"的体验打折；真模型 → 要先把 Key 和调用层搭好（FR-020 的一部分）。
3. **APK 要不要提到 M1？** 你主要用手机的话，网页端在手机上也能跑（浏览器打开），可以先不打包。
4. **§7.2 的 N-01 / N-02 / N-03** —— 三个衍生问题，推荐值已给出，可一并采纳。
